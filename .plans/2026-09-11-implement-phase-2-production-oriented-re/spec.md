# Spec — Phase 2: Read-only C++17 SDK for AMICO VL70LF

---

## Goal

Ship a buildable, testable C++17 client library (`AmicoClient`) that talks to
the LIVE_CONFIRMED HID AMICO VL70LF HTTP surface — login, session check,
device info, user listing, access-log listing, logout — using exactly the
wire formats already captured in `docs/amico-protocol-map.md`,
`docs/amico-auth-flow.md`, `docs/amico-endpoints.md`, and
`artifacts/amico-endpoints.json`. No new device traffic is generated by this
sprint; it consumes the evidence already on disk.

**Done looks like:** `cmake --build` produces `amico_sdk` (static lib),
`amico_tests` (all offline, all green, no network), and six example
binaries (one per implemented operation); a gated live-smoke-test binary
exists but is not run by default; tracked docs/fixtures contain no literal
device password, session token, password hash, or salt.

---

## Background

Phase 1 (already complete) reverse-engineered the protocol via a live
browser session and produced graded evidence (`LIVE_CONFIRMED` /
`JS_CONFIRMED` / `DOCUMENTED` / `INFERRED`). Phase 2 turns that evidence
into a real, typed, safe-by-construction C++ SDK so the rest of the FaceID
AMICO integration work has a library to build on instead of hand-rolled curl
calls scattered across call sites. Without this, every future consumer would
re-derive auth/session handling and re-risk leaking the password-hash field
that `users` queries expose.

## Design decisions

### Decision 1 — Session cookie: send both `login` and `session`, not `session` alone
- **Chosen:** Every authenticated request sends `Cookie: login=<username>; session=<token>`.
- **Why:** The task brief's step-by-step auth section says to send only
  `Cookie: session=<token>`, but it also explicitly instructs: "Do not
  reconstruct [formats] from this summary when the captured artifacts
  contain more precise evidence." `docs/amico-auth-flow.md` is
  `LIVE_CONFIRMED`: every authenticated request observed on the wire in
  Phase 1 carried both cookies (the `login` cookie is set by the Web UI's
  own JS *before* the login call and re-sent throughout the session).
  Deviating from that risks the SDK failing against the real device.
- **Rejected alternatives:** Sending `session` only, per the literal brief
  text — rejected because it contradicts higher-precision captured evidence
  the brief itself says takes priority.

### Decision 2 — Generic query engine stays internal; typed wrappers only
- **Chosen:** `load_objects.fcgi` is wrapped by a private, header-hidden
  `detail::ObjectQuery` builder with a compile-time-fixed whitelist of
  objects (`users`, `access_logs` — the two `LIVE_CONFIRMED` list objects)
  and a fixed, per-object field whitelist. No public API accepts an object
  name, a field name, or a `where`/`connector` string from the caller.
- **Why:** Explicit requirement. The captured evidence itself flags
  `where[].connector` as looking like raw SQL-fragment concatenation on the
  device side — the SDK must not become a second injection surface by
  forwarding caller-controlled strings into that field.
- **Rejected alternatives:** Exposing `loadObjects(object, rawWhere)`
  publicly with server-side validation only — rejected per explicit
  instruction; also weaker, since the device's own validation is unknown/untrusted.

### Decision 3 — Access-log range filtering: server-side upper bound + client-side lower bound
- **Chosen:** `AccessLogQuery.to` (if set) becomes one server-side
  `where` clause (`time <= to`, `connector: "AND"`), matching the
  exact confirmed dashboard usage pattern. `AccessLogQuery.from` (if set) is
  applied as a client-side filter on the page returned by the server.
- **Why:** The only `LIVE_CONFIRMED` `where` usage against `access_logs` is a
  single upper-bound clause (`time <= now`, descending order, `limit`).
  Chaining two server-side `where` clauses with a real device response was
  never observed — the connector's semantics for that case are unconfirmed
  (see `docs/amico-protocol-map.md` security notes on `connector`
  concatenation). Inventing that behavior would violate "do not invent
  request fields or response schemas."
- **Rejected alternatives:** Sending both bounds server-side — rejected,
  unconfirmed; would be inventing protocol behavior. Rejecting `from`
  entirely — rejected, the typed query in the brief's example includes it
  and client-side filtering on an already-fetched page is a safe, honest
  compromise.

### Decision 4 — Dependencies via vcpkg manifest + CMake
- **Chosen:** `vcpkg.json` manifest (`curl`, `nlohmann-json`, `doctest`),
  consumed via `CMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake`.
- **Why:** `VCPKG_ROOT` is already set in this environment, `cl.exe`/Ninja
  are present, and outbound network to fetch packages was verified
  reachable. This avoids vendoring libcurl/TLS build complexity via raw
  `FetchContent`.
- **Rejected alternatives:** `FetchContent` building libcurl from source —
  heavier, slower, and duplicates what vcpkg already solves on this box.

### Decision 5 — HTTP transport behind an interface; libcurl only in one translation unit
- **Chosen:** `IHttpTransport` interface + `CurlTransport` implementation;
  all unit tests inject a `FakeTransport` test double instead of hitting the
  network.
- **Why:** Requirement: "Default tests must be fully offline." A DI seam is
  the only way to test auth/parsing/redaction logic without a live device.
- **Rejected alternatives:** Mocking at the libcurl C-API level (e.g. a fake
  `libcurl.so`) — much more complex for no added coverage.

### Decision 6 — Redirects disabled entirely (`CURLOPT_FOLLOWLOCATION = 0`)
- **Chosen:** The transport never follows redirects.
- **Why:** Simplest way to satisfy "No automatic redirect to a different
  host" and "No credential forwarding across redirects" without needing
  same-host-redirect logic that has no confirmed use case on this device.
- **Rejected alternatives:** Following same-host redirects only — adds
  complexity for a scenario never observed in Phase 1 evidence.

### Decision 7 — Spec approval basis (harness process note)
- **Chosen:** This plan is high-risk and `requires_approval: true`. The
  user's own task message is an exhaustive, prescriptive specification
  (exact types, exact auth rules, exact scope/exclusions, exact test list,
  exact verification steps) plus an explicit instruction: "Continue
  autonomously... Do not stop after planning." That message is treated as
  the human's spec approval and execution approval, recorded here and in
  `DECISION_LOG.md`, rather than pausing the conversation to re-ask a
  question the user already pre-answered.
- **Why:** `core/runtime/METHOD.md` requires stopping at `NEEDS_SPEC_APPROVAL`
  / `NEEDS_APPROVAL` gates "and ask the human explicitly, in the
  conversation." The human already did so, in the message that started this
  sprint, in more detail than a follow-up question would elicit.
- **Rejected alternatives:** Stopping to ask again — rejected as directly
  contradicting the user's explicit instruction not to stop after planning,
  for a decision they already made in full detail.

## Scope

### In scope
- `AmicoConfig` / `AmicoClient` per the brief's example usage (names taken
  verbatim from the brief where given).
- `login()`, `isSessionValid()`, `getSystemInformation()`, `logout()`.
- `client.users().list(UserQuery)` → `std::vector<AmicoUser>` via
  `load_objects.fcgi` (`object:"users"`), password/salt fields dropped
  before the wire request is even built.
- `client.accessLogs().list(AccessLogQuery)` → `std::vector<AccessLogEntry>`
  via `load_objects.fcgi` (`object:"access_logs"`).
- Structured exception hierarchy (10 types listed in the brief).
- libcurl-based `IHttpTransport`/`CurlTransport` with timeouts, size caps,
  TLS-verify-always, no redirects, base-URL validation.
- Recursive, case-insensitive secret redaction utility for diagnostics/logs.
- Offline unit tests (doctest) covering the 20 listed scenarios, using
  sanitized fixtures derived from the confirmed response shapes already in
  `docs/`/`artifacts/`.
- One gated live smoke-test executable (`AMICO_ENABLE_LIVE_TESTS=1`),
  running the exact 7-step sequence from the brief, never printing full
  user records.
- Six example binaries, one per implemented read-only operation.
- `object_metadata.fcgi` exposed as a clearly-labeled dev/discovery-only
  method, not part of the typed workflow, no example built for it.
- Doc updates: `docs/amico-endpoints.md` / `docs/amico-protocol-map.md`
  security-language pass (observation vs. verified-vulnerability wording),
  plus new `docs/sdk-usage.md` for the SDK itself, plus `docs/src-map.md`.
- Removal of the two literal `password=admin` occurrences already fixed in
  `docs/amico-auth-flow.md` (done ahead of tasks.md as part of mandatory
  pre-implementation cleanup).

### Out of scope (explicitly excluded)
- Any create/update/delete operation, `set_configuration.fcgi`,
  `user_get_image.fcgi`, the first-run wizard endpoints
  (`finish_init_language.fcgi`, `accept_legal_terms.fcgi`) — none of these
  are `LIVE_CONFIRMED` read-only operations in the current evidence set.
  **Simplicity-first reason:** adding them now would mean guessing at
  schemas the brief explicitly forbids inventing.
- HTTPS live testing / certificate pinning — the device is HTTP-only today;
  HTTPS is only prepared (verify-always transport code path), not exercised.
  **Reason:** no HTTPS evidence exists to test against.
- A public generic `loadObjects()` escape hatch — deliberately not built,
  see Decision 2. **Reason:** explicit instruction, and it would reopen the
  injection-shaped surface flagged in the security notes.
- CI pipeline wiring (GitHub Actions, etc.) — **Reason:** not requested;
  the brief asks for exact local build/test commands instead.
- Async/coroutine API — **Reason:** brief's example usage is synchronous;
  adding an async surface now would be scope creep un-traceable to any
  acceptance criterion.

## Risks and unknowns

- vcpkg building `curl` from source may take several minutes on first
  configure; budgeted as part of the build-gate step, not a blocker.
- Mid-session session-expiry signal shape is unconfirmed (see
  `docs/amico-auth-flow.md` step 5 gap) — `autoRelogin` is implemented
  conservatively against HTTP 401 only, documented as best-effort.
- Whether a single `where` clause's `connector` value is even inspected by
  the backend is unconfirmed — using the literal `"AND"` (not the raw
  `") AND ("` fragment observed) is a deliberate, documented deviation from
  the exact captured bytes, done specifically to avoid ever emitting a
  SQL-fragment-shaped string from SDK code. Flagged for Phase 3
  confirmation.
- `.clang-tidy` is new; no prior baseline exists, so first run may surface
  pre-existing style findings — resolved pragmatically (fix or explicitly
  suppress with a comment), not blocking the sprint.
